\section{1. Executive Summary of the 30-Day Internship Journey}
Over the course of this 30-day AI/ML Software Engineering Internship at Linkific, my primary growth was learning how to architect, validate, test, and document an end-to-end applied AI software prototype rather than stopping at isolated notebook experiments.

Drawing motivation from my practical experience managing purchase orders and vendor sponsorships (\textbf{INR 60+ Lakhs}) for VIT's Riviera \& Gravitas festivals and my prior Generative AI internship at TForce India Private Limited, I focused the final capstone week on building \textbf{FinDoc-AuditEngine v3.0}---a working FastAPI reference prototype for Accounts Payable (AP) auditing. The prototype demonstrates how regex-based pre-inference PII masking, deterministic 3-Way Line-Item Reconciliation (Invoice vs.\ Purchase Order vs.\ Goods Receipt Note), a 7-feature \texttt{StandardScaler + IsolationForest} model trained on a reproducible seeded synthetic baseline ($N=1{,}000$), and local single-feature perturbation attribution work together inside a clean, testable web application.

\section{3. Core Technical Skills Acquired}
\begin{enumerate}[leftmargin=0.22in, itemsep=3pt]
    \item \textbf{Combining Deterministic Domain Rules with Unsupervised Anomaly Scoring:} Learned when to apply deterministic rule logic (\texttt{ReconciliationMatcher} enforcing configured $\$0.01$ unit-rate and $\$0.05$ subtotal rules) versus statistical isolation (\texttt{AnomalyScorer} surfacing unusual multi-feature combinations such as offshore Net-1 rush payments).
    \item \textbf{Distinguishing Synthetic Baselines from Calibrated Production Models:} Designed a reproducible seeded synthetic dataset ($N=1{,}000$, \texttt{random\_state=42}) to fit the prototype's 7-feature \texttt{IsolationForest} and implemented local perturbation attribution:
    \[
        \Delta R_k(\mathbf{x}) = \max\!\left(0,\; R(\mathbf{x}) - R\!\left(\mathbf{x}^{(k \leftarrow \mu_k)}\right)\right)
    \]
    Crucially, I learned to communicate clearly that the resulting $0\text{--}100$ score is an \textit{engineered anomaly-risk indicator} for the prototype rather than a calibrated probability of fraud.
    \item \textbf{Schema Validation, Custom Exceptions \& Automated Verification:} Built Pydantic v2 cross-field validators (\texttt{@model\_validator}), structured \texttt{FinDocAuditException} JSON error handlers, and automated PyTest suites where all collected tests pass (\texttt{28 passed} in Day 29; \texttt{33 passed} in Day 30).
\end{enumerate}

\section{4. Major Engineering Challenges Overcome}
\begin{enumerate}[leftmargin=0.22in, itemsep=4pt]
    \item \textbf{Challenge 1 --- Decoupling Frontend DOM Table Edits from Static Preset Objects:}
    \begin{itemize}[leftmargin=0.18in, itemsep=1pt]
        \item \textit{Root Cause:} In early iterations of the dashboard, submitting an audit reused the preset Purchase Order's line-item array, so manual edits to SKU rates or dock rejected quantities in the HTML table did not alter backend reconciliation.
        \item \textit{Engineering Fix:} Implemented \texttt{collectLineItemsFromDOM()} in \texttt{dashboard.js} to construct independent \texttt{InvoicePayload} and \texttt{PurchaseOrderRecord} line-item arrays directly from live \texttt{<input>} cells, verified by a dedicated multi-line PyTest regression test.
    \end{itemize}
    \item \textbf{Challenge 2 --- Preventing Dollar Magnitude Dominance in Isolation Trees:}
    \begin{itemize}[leftmargin=0.18in, itemsep=1pt]
        \item \textit{Root Cause:} Raw USD invoice totals ($\$432$ to $\$49{,}500$) spanned orders of magnitude compared to bounded ratios ($[0,1]$), skewing random split thresholds.
        \item \textit{Engineering Fix:} Applied logarithmic compression $\ln(1 + \text{Total}_{\text{USD}})$ and standardized all 7 features via \texttt{StandardScaler} prior to fitting the 200-tree \texttt{IsolationForest}.
    \end{itemize}
    \item \textbf{Challenge 3 --- IEEE 754 Floating-Point Rounding in Multi-Line Tax Arithmetic:}
    \begin{itemize}[leftmargin=0.18in, itemsep=1pt]
        \item \textit{Root Cause:} Binary floating-point products occasionally differed by fractions of a cent on multi-SKU invoices with $18\%$ GST.
        \item \textit{Engineering Fix:} Enforced two-decimal rounding at line-item boundaries and configured a deterministic $\$0.05$ \texttt{SUBTOTAL\_TOLERANCE} across Pydantic validation and 3-way matching.
    \end{itemize}
    \item \textbf{Challenge 4 --- Maintaining Factual & Test-Count Consistency Across Deliverables:}
    \begin{itemize}[leftmargin=0.18in, itemsep=1pt]
        \item \textit{Root Cause:} Adding Day 29 and Day 30 route verification tests increased collected test counts from $25/30$ to $28/33$.
        \item \textit{Engineering Fix:} Audited and synchronized every README, slide, PDF report, and terminal screenshot to report exact verified PyTest counts (\texttt{28 passed} in Day 29; \texttt{33 passed} in Day 30) and honest prototype boundaries.
    \end{itemize}
\end{enumerate}

\section{6. Key Lessons Learned}
\begin{enumerate}[leftmargin=0.22in, itemsep=4pt]
    \item \textbf{Precision in Technical Claims Builds Engineering Credibility:} Describing a prototype accurately---stating that the ledger is in-memory, the ML baseline is synthetic, and test pass rate is distinct from code coverage---makes technical defenses significantly stronger during mentor and panel reviews.
    \item \textbf{Automated Tests Must Be Re-Verified After Every Change:} Whenever API endpoints or documentation checks are added, running \texttt{python -m pytest tests -q} and updating screenshots immediately prevents documentation drift.
    \item \textbf{High-Contrast Institutional UI Improves Live Demonstrations:} Designing a clean light-theme tabular workbench made SKU unit-rate variances, GRN dock rejections, and perturbation attribution bars immediately readable during live walkthroughs.
\end{enumerate}
